# PATCHES.md — реестр правок в upstream-файлах

Этот файл читает тот, кто разрешает конфликт после ребейза на новый upstream —
человек или агент. Предполагается, что у читателя на руках **только конфликтный
хунк**, без контекста и без истории обсуждения.

Поэтому здесь:

- **нет опоры на номера строк** — они протухают первыми, номера даны только как
  подсказка «примерно тут»;
- у каждой правки записан **якорь** (код upstream, к которому она крепится),
  **зачем** она нужна и **какой инвариант** обязана сохранить;
- сказано, **что делать, если якорь исчез** — куда переносить и по какому
  признаку выбирать новое место.

Общий контекст и обоснование архитектуры — в [PLAN.md](PLAN.md).

---

## Как это работает

Каждая наша строка в upstream-файле помечена маркером:

```go
fllcker.Track(ctx, user.Email) // [fllcker:FLK-001]
```

Маркер — это grep-якорь. По нему [scripts/check-patches.sh](scripts/check-patches.sh)
проверяет, что после ребейза все патчи на месте: `go build` пропажу строки не
заметит, а проверка маркеров заметит.

```bash
$ bash scripts/check-patches.sh
ok       FLK-001  2 site(s)
ok       FLK-002  1 site(s)
...
```

Список ID скрипт вытаскивает **из этого файла**, из заголовков `## FLK-NNN`.
Значит карточка и проверка не могут разъехаться: добавил патч — заведи карточку,
иначе он не проверяется; удалил патч — удали карточку, иначе проверка красная.

---

## Правила разрешения конфликтов

Читай прежде, чем трогать любой из патчей ниже.

1. **Наши строки помечены маркером.** Если в конфликте есть строка с
   `[fllcker:NNN]` — это наше, не выбрасывать.
2. **Приоритет у upstream.** При конфликте берём его версию окружающего кода и
   заново вставляем в неё нашу строку по якорю. Не наоборот.
3. **Инвариант важнее места.** Если код переехал, но инвариант из карточки можно
   соблюсти в новом месте — переносим. Если соблюсти нельзя — **не выдумывать
   обходной путь**, а остановиться и завести issue. Молча поставленный «почти
   туда же» хук хуже отсутствующего: он выглядит рабочим.
4. **Никогда не расширять скоуп.** Все операции идут по паре `(email, ip)`.
   Правка, после которой что-то работает по одному только `ip`, — критический
   баг (см. FLK-000).
5. **Проверять после переноса.** `go build ./...`, `go test ./app/fllcker/...`,
   `bash scripts/check-patches.sh`.

## Файлы, которые форк держит полностью своими

Не патчи, а полная замена. Конфликт здесь разрешается **всегда в нашу пользу**,
содержимое upstream не имеет значения.

| Файл | Почему |
|---|---|
| `README.md` | титульная страница репозитория должна описывать форк, а не Project X |
| `UPSTREAM_TAG` | наш файл, upstream о нём не знает |

⚠️ **Ловушка при ребейзе: стороны инвертированы.** Во время `git rebase`
`--ours` — это новая база (upstream), а `--theirs` — наш коммит, который
переносится. То есть «оставить наш README» пишется как:

```bash
git checkout --theirs -- README.md
```

Интуитивное `--ours` здесь возьмёт как раз upstream'овский вариант. Синк-воркфлоу
разрешает этот случай сам ([fllcker-sync-upstream.yml](.github/workflows/fllcker-sync-upstream.yml)),
но если разбираете конфликт руками — помните про инверсию.

## FLK-000 — сквозной инвариант (не патч)

Не относится к конкретному файлу, но нарушается легче всего.

> **Ни одна операция не действует на IP-адрес сам по себе.** Реестр и баны
> ключуются парой `(email, ip)`. `IsBanned` принимает оба аргумента. Хендлы для
> закрытия берутся только из `users[email][ip]`.

**Почему это критично.** За одним публичным адресом сидит CGNAT оператора,
корпоративный NAT, общий Wi-Fi. Там могут быть сотни наших же юзеров. Операция
по одному `ip` положит их всех разом.

**Как ломается.** Обычно через «оптимизацию»: кто-то заводит обратный индекс
`ip → сессии`, чтобы не обходить мапу. Компилируется, тесты на кик проходят,
изоляция ломается молча.

**Что защищает.** Тест `TestKickIsolatedByUser` в `app/fllcker/registry_test.go`.
Если он удалён или изменён — это красный флаг, а не уборка.

## FLK-001 — регистрация сессии в диспетчере (getLink)

| | |
|---|---|
| Файл | `app/dispatcher/default.go` |
| Ориентир | ~строка 183, функция `getLink` |
| Диф | +1 строка |

**Якорь.** Внутри `getLink`, в блоке `if user != nil && len(user.Email) > 0 {`,
рядом с существующим вызовом:

```go
if p.Stats.UserOnline {
    trackOnlineIP(ctx, d.stats, user.Email, sessionInbound.Source.Address.String())
}
```

**Наша строка** — сразу после этого блока, **вне** `if p.Stats.UserOnline`:

```go
fllcker.Track(ctx, user.Email) // [fllcker:FLK-001]
```

**Зачем.** Точка, где одновременно доступны email, source IP и закрываемый conn
(через `session.InboundFromContext(ctx)`).

`getLink` — это путь `Dispatch`, по нему приходят **VMess, Trojan,
Shadowsocks**. Ни один из протоколов нашего прода сюда не попадает — они все
идут через FLK-002. Патч держим ради полноты: если завтра поднимем trojan-инбаунд,
без него он молча выпадет из реестра.

**Инвариант.** Вызов обязан быть **вне** `if p.Stats.UserOnline`. Кик не должен
зависеть от того, включена ли статистика в policy — иначе на конфиге без
`"stats"` API молча вернёт пустой список вместо ошибки.

**Если якорь исчез.** Ищем любое место в `getLink`, где уже известен
`user.Email` и в контексте лежит `session.Inbound` с заполненным `Conn`. Условие
проверяемое: `session.InboundFromContext(ctx).Conn != nil` на момент вызова.
Если upstream убрал `Conn` из `session.Inbound` — инвариант нарушен, **stop,
issue**: без него кик невозможен в принципе и нужен другой дизайн.

## FLK-002 — регистрация сессии в диспетчере (WrapLink)

| | |
|---|---|
| Файл | `app/dispatcher/default.go` |
| Ориентир | ~строка 217, функция `WrapLink` |
| Диф | +1 строка |

**Якорь.** Тот же паттерн, что в FLK-001, но в `WrapLink`:

```go
if p.Stats.UserOnline {
    trackOnlineIP(ctx, statsManager, user.Email, sessionInbound.Source.Address.String())
}
```

**Наша строка:**

```go
fllcker.Track(ctx, user.Email) // [fllcker:FLK-002]
```

**Зачем.** `WrapLink` — путь `DispatchLink`, и по нему идут **оба протокола
прода**:

- VLESS — [proxy/vless/inbound/inbound.go:633](proxy/vless/inbound/inbound.go#L633)
  (`dispatch.DispatchLink`), и отдельно reverse-режим на
  [строке 630](proxy/vless/inbound/inbound.go#L630), где `WrapLink` зовут напрямую;
- Hysteria2 — [proxy/hysteria/server.go:125](proxy/hysteria/server.go#L125) и
  [:167](proxy/hysteria/server.go#L167).

**Это главный хук, он несёт весь боевой трафик.** Не перепутать с FLK-001:
интуиция «VLESS идёт через Dispatch» неверна, VLESS дispatch'ится линком.

**Инвариант.** Тот же, что у FLK-001: вне `if p.Stats.UserOnline`.

**Если якорь исчез.** Если `getLink` и `WrapLink` слили в одну функцию —
патч остаётся один, второй удаляем и **правим этот файл**, не оставляя мёртвую
карточку.

## FLK-003 — проверка бана в VLESS

| | |
|---|---|
| Файл | `proxy/vless/inbound/inbound.go` |
| Ориентир | ~строка 531, функция `Process` |
| Диф | +3 строки |

**Якорь.** После разбора запроса и присвоения юзера:

```go
inbound.Name = "vless"
inbound.User = request.User
inbound.VlessRoute = net.PortFromBytes(userSentID[6:8])
```

**Наши строки** — сразу после `inbound.User = request.User`:

```go
// [fllcker:FLK-003]
if fllcker.IsBanned(request.User.Email, inbound.Source.Address.String()) {
	return errors.New("fllcker: ip temporarily banned").AtInfo()
}
```

**Зачем.** Без блокировки кик бесполезен: клиент переподключается за ~200 мс.
Покрывает и TCP REALITY, и XHTTP REALITY — оба идут через один `Process`.

**Инвариант.** Строго **после** успешного разбора запроса. Раньше по коду идёт
fallback-ветка (обработка ошибок парсинга, `pfb[path]`); если вставить проверку
до неё, забаненный IP уйдёт в fallback вместо разрыва — то есть на сайт-заглушку
вместо отказа. Это не критично, но означает, что бан не работает.

**Если якорь исчез.** Условие для нового места: `request.User` уже установлен,
`inbound.Source` валиден, fallback-ветка позади, возврат ошибки закрывает
соединение. Возврат `error` из `Process` — это и есть механизм разрыва, ничего
дополнительно закрывать не надо.

## FLK-004 — проверка бана в Hysteria2

| | |
|---|---|
| Файл | `proxy/hysteria/server.go` |
| Ориентир | ~строка 101, функция `Process` |
| Диф | +3 строки |

**Якорь.** Блок извлечения юзера из QUIC-коннекта:

```go
if v, ok := iConn.(interface{ User() *protocol.MemoryUser }); ok {
	user := v.User()
	if user != nil {
		inbound.User = user
		inbound.VlessRoute = user.Account.(*account.MemoryAccount).VR
	}
}
```

**Наши строки** — сразу после этого блока, **до** ветвления на
`hysteria.InterConn`/UDP и TCP:

```go
// [fllcker:FLK-004]
if e := inbound.User.Email; e != "" && fllcker.IsBanned(e, inbound.Source.Address.String()) {
	return errors.New("fllcker: ip temporarily banned").AtInfo()
}
```

**Зачем.** Аутентификация hysteria происходит на уровне QUIC, а не в `Process`,
поэтому проверка из FLK-003 сюда не достаёт. Нужен свой хук.

**Инварианты — два, оба обязательны:**

1. **Проверка на непустой `Email`.** Выше по коду стоит
   `inbound.User = &protocol.MemoryUser{}` — пустой юзер. Если юзер не
   распознан, `Email` остаётся `""`. Без проверки на непустоту один бан на
   пустой email положит все нераспознанные коннекты разом.
2. **До обеих веток.** Ниже код расходится на UDP (`hysteria.InterConn`) и TCP.
   Проверка в одной ветке оставляет вторую дырявой.

**Про ограничение (не баг, а свойство).** `inbound.Conn` для hysteria — это
QUIC-**стрим**, а не сессия. Кик рвёт стрим, клиент остаётся аутентифицирован и
может открыть новый — но упрётся в эту проверку. Поэтому для hysteria кик
работает как «глухая стена на время бана», а не как разрыв. Не пытаться
«починить» это закрытием QUIC-сессии без отдельного обсуждения.

**Если якорь исчез.** Если upstream перенёс аутентификацию hysteria внутрь
`Process` — проверку ставим по правилам FLK-003 и удаляем оговорку про пустой
email, предварительно убедившись, что она больше не нужна.

## FLK-005 — регистрация сервиса в конфиге

| | |
|---|---|
| Файл | `infra/conf/api.go` |
| Ориентир | функция `Build`, `switch strings.ToLower(s)` |
| Диф | +1 импорт, +2 строки |

**Якорь.**

```go
case "routingservice":
	services = append(services, serial.ToTypedMessage(&routerservice.Config{}))
```

**Наши строки** — новая ветка в том же `switch`:

```go
case "fllckerservice": // [fllcker:FLK-005]
	services = append(services, serial.ToTypedMessage(&fllckerservice.Config{}))
```

плюс импорт:

```go
fllckerservice "github.com/xtls/xray-core/app/fllcker/command" // [fllcker:FLK-005]
```

**Зачем.** Без этого `"services": ["FllckerService"]` в конфиге молча
игнорируется — `switch` без `default` не ругается на неизвестное имя. Симптом:
API поднялся, метода нет.

**Инвариант.** Имя ветки — в нижнем регистре (`strings.ToLower` выше по коду).

## Чеклист после ребейза

```bash
bash scripts/check-patches.sh      # все маркеры на месте
go build ./...
go test ./app/fllcker/...
go vet ./app/fllcker/...
```

Дальше — смоук на стенде: поднять конфиг с тремя инбаундами, подключиться,
`ListSessions` должен показать сессию, `Kick` — оборвать её. Автотесты этого не
покрывают: они проверяют логику реестра, а не то, что хуки стоят в правильных
местах.
