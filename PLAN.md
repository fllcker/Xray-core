# PLAN.md — форк xray-core: мягкое противодействие шарингу подписки

Форк xray-core для VPN-сервиса. Задача: не банить юзеров за шаринг, а делать
шаринг **неудобным** — сбрасывать лишние сессии с коротким (5–10 с) запретом на
переподключение с того же IP.

Базовый upstream: `7d214f8` (2026-08-12).

**Протоколы в проде:** VLESS TCP REALITY, VLESS XHTTP REALITY, Hysteria2.

## 1. Цель и принцип

**Не бан, а трение.** Честный юзер не должен ничего заметить. Шарящий получает
постоянные обрывы, но не теряет доступ и не идёт в поддержку с «за что забанили».

Ядро даёт только **примитив**: «закрой соединения юзера X с IP Y и не пускай его
обратно N секунд». Вся политика (сколько IP разрешено, какой считать «лишним»,
как долго держать) живёт на бэкенде, а не в core. Это принципиально: политику
хочется менять без пересборки и передеплоя xray.

## 2. Что уже есть в upstream и почему этого мало

### 2.1 Учёт онлайна

`app/stats/online_map.go` — refcount-мапа IP на юзера. `GetStatsOnlineIpList`
отдаёт `map<ip, lastSeen>`, где `lastSeen` — время **последнего** `AddIP`, а не
время подключения.

Регистрация — в диспетчере, [app/dispatcher/default.go:224-230](app/dispatcher/default.go#L224-L230):

```go
func trackOnlineIP(ctx context.Context, sm stats.Manager, email, ip string) {
	name := "user>>>" + email + ">>>online"
	if om, _ := sm.GetOrRegisterOnlineMap(name); om != nil {
		om.AddIP(ip)
		context.AfterFunc(ctx, func() { om.RemoveIP(ip) })
	}
}
```

### 2.2 Почему онлайн «залипает»

Цепочка, из-за которой IP исчезает с непредсказуемой задержкой:

1. Учёт ведётся **на каждый проксируемый поток**, а не на TCP-коннект клиента.
2. Refcount → IP уходит из мапы только когда завершился **последний** поток.
3. Контекст потока отменяется, когда вернётся `proxy.Process` —
   [app/proxyman/inbound/worker.go:123-127](app/proxyman/inbound/worker.go#L123-L127).
4. `Process` висит до реального закрытия сокета либо до `connIdle`, дефолт
   **300 с** — [features/policy/policy.go:131](features/policy/policy.go#L131).

Итог: задержка = максимум по остаткам idle-таймаутов висящих коннектов.
Отсюда и ложные срабатывания: после смены сети старый IP живёт рядом с новым до
5 минут.

### 2.3 Чего нет совсем

- Нет реестра живых соединений — нечего закрывать.
- `RemoveUser` **не рвёт живые сессии**,
  [proxy/vless/inbound/inbound.go:245-248](proxy/vless/inbound/inbound.go#L245-L248)
  только чистит валидатор. Трюк «удалить + добавить юзера» как способ кика не
  работает: старые коннекты доживают до `connIdle`.

## 3. Ключевое наблюдение

Есть ровно одна точка, где одновременно доступны **email, source IP и убиваемый
conn** — тот же `trackOnlineIP`. Через `session.InboundFromContext(ctx)`
доступны:

- `.User.Email` — идентичность,
- `.Source` — IP клиента,
- `.Conn` — сырой транспортный коннект, кладётся в
  [app/proxyman/inbound/worker.go:116](app/proxyman/inbound/worker.go#L116),
  поле объявлено в [common/session/session.go:52-53](common/session/session.go#L52-L53).

Значит реестр строится **без единой новой точки перехвата** — только рядом с
существующей.

## 4. Архитектура

### 4.1 Пространство имён: `fllcker`

Все добавления форка живут под собственным именем, а не под функциональным вроде
`kick`. Причины:

- API будет расти — сюда лягут будущие методы, не только кик;
- имя гарантированно не столкнётся с upstream, если XTLS однажды заведёт свой
  `app/kick` или `KickService`;
- в `grpcurl`/рефлексии сразу видно, что метод не из ванильного xray.

| Что | Значение |
|---|---|
| Пакет ядра | `app/fllcker` |
| Пакет API | `app/fllcker/command` |
| Proto package | `xray.app.fllcker.command` |
| gRPC-сервис | `FllckerService` |
| Имя в конфиге | `"services": ["FllckerService"]` |
| Ветка в `api.go` | `case "fllckerservice"` |

⚠️ Имя сервиса попадает в wire-путь gRPC
(`/xray.app.fllcker.command.FllckerService/Kick`). Переименование потом сломает
клиент на бэкенде — выбираем один раз.

### 4.2 Раскладка файлов

Всё новое — в новых файлах. В upstream-файлах правки измеряются строками.

```text
app/fllcker/
  registry.go       — реестр живых сессий
  ban.go            — временные баны пар (email, ip)
  fllcker.go        — публичное API пакета (Track / Kick / IsBanned / Snapshot)
  registry_test.go
  ban_test.go
app/fllcker/command/
  config.proto      — Config{}
  command.proto     — FllckerService
  command.go        — реализация gRPC
  *.pb.go           — генерируется
```

### 4.3 Решение: глобальный синглтон, а не core-feature

Реестр — package-level синглтон в `app/fllcker`, не зарегистрированная
`core.Feature`.

**Почему:** feature требует правок в `core/`, инъекции зависимости в
`DefaultDispatcher.Init`, конфига и плюс-минус десятка строк в чужих файлах.
Синглтон даёт диф в единицы строк. Для форка, который планируется вечно
ребейзить на upstream, это решающий аргумент.

**Цена:** один реестр на процесс. Тесты, поднимающие несколько `core.Instance`
в одном процессе, разделят состояние. Для сервера это не важно; для наших
собственных тестов добавим `fllcker.Reset()`.

Альтернатива на будущее — в §12.

### 4.4 Модель данных

```go
// registry.go
type handle struct {
	id   uint64
	conn net.Conn
}

// Агрегат по IP: именно он отдаётся в ListSessions.
type ipState struct {
	since    int64                // первый коннект с этого IP
	lastSeen int64                // последний новый поток с этого IP
	handles  map[uint64]*handle
}

type registry struct {
	mu     sync.RWMutex
	users  map[string]map[string]*ipState // email -> ip -> состояние
	nextID atomic.Uint64
}
```

`since` пишется один раз при создании `ipState`, `lastSeen` — на каждую
регистрацию нового потока. Держим `lastSeen` явным полем, а не выводим как
максимум по живым handle: короткие потоки успевают умереть, и производная
величина «состарилась» бы на активно используемом IP. Зачем нужны оба поля —
в §9.

Несколько потоков могут делить один физический conn (Mux.cool, XHTTP) — будет
несколько handle с одним `conn`. Повторный `Close()` безвреден, дедуп не нужен.

```go
// ban.go
type banRegistry struct {
	mu     sync.RWMutex
	bans   map[string]map[string]int64 // email -> ip -> unban (unix nano)
	active atomic.Int64                // быстрый выход, когда банов нет
}
```

### 4.5 Инвариант: скоуп всегда `(email, ip)`, никогда просто `ip`

**Ни одна операция не действует на IP-адрес сам по себе.** И реестр, и баны
ключуются парой: сначала email, потом ip. `IsBanned` принимает оба аргумента,
хендлы для закрытия берутся из `users[email][ip]`.

Пример, который должен работать именно так:

```text
user1 → 1.1.1.1
user2 → 1.1.1.1   (тот же адрес, другой юзер)

Kick(email=user1, ip=1.1.1.1, ban_seconds=5)
  → рвутся только коннекты user1
  → бан ставится только на пару (user1, 1.1.1.1)
  → user2 не замечает вообще ничего
```

Это не косметика. За одним публичным адресом сидит CGNAT оператора, корпоративный
NAT, общая Wi-Fi сеть — там могут быть сотни наших же юзеров. Глобальный бан по IP
положил бы их всех разом, и это был бы самый дорогой баг во всей затее.

По структурам данных инвариант соблюдается автоматически: до чужих хендлов
просто нет пути. Но он должен быть закреплён тестами (см. §8), потому что
«оптимизация» вида «а давайте индекс по ip для скорости» ломает его молча.

## 5. Покрытие протоколов

Три протокола прода ведут себя по-разному, и это определяет, куда ставить хуки.

| Протокол | Реестр (Track) | Где проверять бан | Кик закрытием conn |
|---|---|---|---|
| VLESS TCP REALITY | ✅ работает | VLESS `Process` | ✅ рвёт TCP-коннект |
| VLESS XHTTP REALITY | ✅ работает | VLESS `Process` (тот же хук) | ⚠️ Q1 — нужен стенд |
| Hysteria2 | ✅ работает | Hysteria `Process` (отдельный хук) | ⚠️ рвёт QUIC-стрим, не сессию |

### 5.1 Почему реестр работает везде

Hysteria2 в xray-core обслуживается **тем же `tcpWorker`**: в
[worker.go:134-140](app/proxyman/inbound/worker.go#L134-L140) в контекст кладётся
валидатор, дальше обычный `internet.ListenTCP` → `w.callback(conn)`. Значит
`session.Inbound.Conn` заполняется на [worker.go:116](app/proxyman/inbound/worker.go#L116)
и для hysteria тоже.

Все три протокола прода идут через `DispatchLink` → `WrapLink`, то есть через
один хук FLK-002:

- VLESS (и TCP, и XHTTP) — [inbound.go:633](proxy/vless/inbound/inbound.go#L633),
  плюс reverse-режим зовёт `WrapLink` напрямую на [строке 630](proxy/vless/inbound/inbound.go#L630);
- Hysteria2 — [server.go:125](proxy/hysteria/server.go#L125) и [:167](proxy/hysteria/server.go#L167).

Второй хук, FLK-001 в `getLink`, обслуживает путь `Dispatch`: VMess, Trojan,
Shadowsocks. На нашем проде он не нужен, но ставим сразу — иначе поднятый позже
trojan-инбаунд молча выпадет из реестра.

### 5.2 Почему для Hysteria2 нужен отдельный хук бана

Аутентификация hysteria происходит **на уровне QUIC**, а не в `Process`. Юзер
достаётся уже готовым из коннекта —
[proxy/hysteria/server.go:94-101](proxy/hysteria/server.go#L94-L101):

```go
if v, ok := iConn.(interface{ User() *protocol.MemoryUser }); ok {
	user := v.User()
	if user != nil {
		inbound.User = user
		...
	}
}
```

Поэтому проверка бана из VLESS сюда не достаёт — нужен свой хук, сразу после
этого блока и **до обеих веток** (`hysteria.InterConn`/UDP и TCP).

### 5.3 Ограничение кика для Hysteria2

`inbound.Conn` для hysteria — это **QUIC-стрим**, а не QUIC-сессия. Закрытие
рвёт стрим, но клиент остаётся аутентифицированным на транспортном уровне и
может открывать новые стримы.

Практически это не ломает схему: каждый новый стрим проходит через `Process`, где
стоит проверка бана, и будет отбит. То есть для hysteria кик работает не как
«разрыв», а как «глухая стена на время бана» — с точки зрения юзера разница
незаметна. Но `closed` в ответе для hysteria означает «закрыто стримов», а не
«разорвано клиентов», и это надо помнить, читая метрики.

### 5.4 XHTTP: замечание про Source

При XHTTP за CDN/nginx `inbound.Source` — это адрес фронта, а не клиента, и вся
схема разваливается. У нас XHTTP идёт **напрямую с REALITY**, так что вопрос
закрыт. Но если когда-нибудь появится CDN-фронт — сначала прокинуть реальный IP
и только потом включать кик на этом инбаунде.

## 6. Точки интеграции (весь диф в upstream-файлах)

### 6.1 Регистрация сессий — `app/dispatcher/default.go`

По одной строке в `getLink` (рядом со строкой 183) и в `WrapLink` (рядом со
строкой 217), **вне** блока `if p.Stats.UserOnline` — реестр нужен независимо от
того, включена ли статистика:

```go
fllcker.Track(ctx, user.Email)
```

`fllcker.Track` сам достаёт `session.InboundFromContext(ctx)`, берёт `.Source` и
`.Conn`, регистрирует handle и вешает `context.AfterFunc(ctx, release)` —
ровно тот же жизненный цикл, что у `OnlineMap`. Цикла импортов нет:
`app/fllcker` тянет только `common/session` и `common/net`.

**Диф: +2 строки, +1 импорт.**

### 6.2 Проверка бана — VLESS

`proxy/vless/inbound/inbound.go`, сразу после `inbound.User = request.User`
([inbound.go:531](proxy/vless/inbound/inbound.go#L531)):

```go
if fllcker.IsBanned(request.User.Email, inbound.Source.Address.String()) {
	return errors.New("fllcker: ip temporarily banned").AtInfo()
}
```

Возврат ошибки здесь просто закрывает коннект — fallback-логика находится выше
по коду, в ветке ошибки парсинга запроса, и не заденется. Покрывает и TCP, и
XHTTP: оба идут через один `Process`.

**Диф: +3 строки, +1 импорт.**

### 6.3 Проверка бана — Hysteria2

`proxy/hysteria/server.go`, сразу после блока извлечения юзера
([server.go:94-101](proxy/hysteria/server.go#L94-L101)) и до ветвления на
UDP/TCP:

```go
if fllcker.IsBanned(inbound.User.Email, inbound.Source.Address.String()) {
	return errors.New("fllcker: ip temporarily banned").AtInfo()
}
```

Осторожно: `inbound.User` здесь инициализирован пустым `&protocol.MemoryUser{}`
и остаётся таким, если юзер не распознан. Проверять только при непустом
`Email`, иначе забаненный пустой email положит анонимные коннекты.

**Диф: +3 строки, +1 импорт.**

### 6.4 Ключ IP — всегда `Source.Address.String()`

И в реестре, и в банах, и во всех трёх хуках. Тот же ключ, что у `OnlineMap`,
иначе IPv6 разъедется по форматированию и бан не совпадёт с записью.

## 7. gRPC API

```proto
service FllckerService {
  rpc Kick(KickRequest) returns (KickResponse) {}
  rpc ListSessions(ListSessionsRequest) returns (ListSessionsResponse) {}
  rpc ListBans(ListBansRequest) returns (ListBansResponse) {}
  rpc Unban(UnbanRequest) returns (UnbanResponse) {}
}

message KickRequest {
  string email = 1;
  repeated string ips = 2;  // пусто = все IP юзера
  uint32 ban_seconds = 3;   // 0 = кик без бана
}

message KickResponse {
  int32 closed = 1;         // сколько коннектов/стримов закрыли (см. §5.3)
  int64 banned_until = 2;   // unix, 0 если бана нет
}

message SessionIP {
  string ip = 1;
  int32 conns = 2;          // живых коннектов с этого IP
  int64 since = 3;          // самый ранний коннект — «когда IP появился»
  int64 last_seen = 4;      // последний новый поток — «признак жизни»
  int64 banned_until = 5;   // 0 если не забанен
}

message ListSessionsRequest { string email = 1; }   // пусто = все юзеры
message UserSessions { string email = 1; repeated SessionIP ips = 2; }
message ListSessionsResponse { repeated UserSessions users = 1; }
```

`ban_seconds` — именно то, что нужно бэкенду: «откинуть на 5–10 секунд».
Порядок операций в `Kick` важен — **сначала ставим бан, потом закрываем
коннекты**, иначе клиент успеет переподключиться в окне между двумя шагами.

`ips` — список, а не один адрес. По логам у одного uuid бывает до 5 сессий, и
типовая операция — «выбить все кроме самого нового». Пять отдельных RPC оставляют
окно: пока летит второй вызов, клиент, выбитый первым, уже может вернуться с
адреса, которого в списке вызывающего ещё нет. Один вызов банит **все** адреса
до того, как закроет первый коннект, и сжимает это окно до одного round-trip.
Пустой список = все адреса юзера.

`ListSessions` полезнее текущего `GetStatsOnlineIpList`: отдаёт число живых
коннектов на IP, время первого и время последнего, а не одно перезаписываемое
`lastSeen`.

## 8. Открытые вопросы

**Q1. XHTTP: убивает ли `Close()` логическую сессию?** ⚠️ открыт

Для `stream-up`/`packet-up` `inbound.Conn` — обёртка над HTTP-стримом
(`transport/internet/splithttp/connection.go`). Закрытие одного стрима может не
уронить сессию целиком. Блокировка при этом работает в любом случае (§6.2), под
вопросом только немедленность разрыва. **Нужен стендовый тест**, до него XHTTP
не считаем покрытым по кику.

**Q2. Нужен ли `Unban` в v1?** Баны по 5–10 с истекают сами. `Unban` нужен
только для отладки и для «ой, кикнули не того». Стоит дёшево, оставляем.

## 9. Порядок работ

| # | Шаг | Итог |
|---|-----|------|
| 1 | Снизить `connIdle` до 60–120 с в конфиге прода | Точность онлайна вырастает сразу, без форка |
| 2 | `app/fllcker`: registry + ban + юнит-тесты | Логика проверена в отрыве от ядра |
| 3 | Хук `Track` в диспетчере | `ListSessions` уже отдаёт правду |
| 4 | proto + генерация + gRPC-сервис | API поднимается, `closed` считается |
| 5 | Проверка бана в VLESS | Кик перестаёт быть бесполезным для TCP и XHTTP |
| 6 | Проверка бана в Hysteria2 | Третий протокол закрыт |
| 7 | Регистрация в `api.go` и `distro/all` | Включается через конфиг |
| 8 | Стенд: два клиента, один email, все 3 протокола | Проверка кика и Q1 |
| 9 | CI: sync-upstream + release (§13) | Форк перестаёт гнить |
| 10 | README (§14) | Можно ставить на сервер по инструкции |
| 11 | CLI `xray api fllcker kick` | Отладка без grpcurl |

Шаг 1 делается **первым и отдельно** — он не требует форка вообще и один
закрывает большую часть ложных срабатываний.

### Обязательные тесты на шаге 2

Первый — про инвариант из §4.5, он важнее всех остальных:

- **Изоляция по юзеру.** `user1` и `user2` с одним и тем же IP. Кик `user1` не
  трогает ни коннекты, ни баны `user2`. Проверять оба направления: и что
  соединения живы, и что `IsBanned(user2, ip)` возвращает `false`.
- Кик с `ban_seconds=0` рвёт коннекты и не ставит бан.
- Кик с пустым `ip` рвёт все IP юзера.
- Бан истекает сам: `IsBanned` даёт `false` после `ban_seconds`.
- Бан ставится **до** закрытия коннектов (§11) — проверяется тем, что сразу
  после возврата `Kick` повторный вход с того же IP уже отбит.
- Пустой email не банится и не матчится (защита от §6.3).
- Несколько handle на одном `conn` (Mux) — повторный `Close()` не паникует,
  `closed` в ответе не задваивается.
- Release по `context.AfterFunc` убирает `ipState`, когда ушёл последний handle.
- `IsBanned` на пустом банлисте не берёт мьютекс (быстрый путь через
  `atomic.Int64`).

### Генерация protobuf

**Не запускать `go run ./infra/vprotogen/main.go -pwd .`** — он обходит всё
дерево и перегенерирует *каждый* `.pb.go`. Версия protoc попадает в шапку
сгенерированных файлов, так что при несовпадении версий получится диф на сотни
файлов и гарантированный конфликт на следующем ребейзе.

Генерируем только свой файл, теми же флагами, что использует vprotogen:

```bash
protoc --go_out=. --go_opt=paths=source_relative \
       --go-grpc_out=. --go-grpc_opt=paths=source_relative \
       app/fllcker/command/command.proto
```

⚠️ **Версия protoc.** В репозитории файлы сгенерированы `protoc v6.33.5`, а наш
`command.pb.go` — тем, что стоит локально (`v7.35.0--rc1`, release candidate).
На корректность кода это не влияет — Go-код пишет `protoc-gen-go`, а он у нас
ровно той же версии `v1.36.11`, что и в репозитории; protoc только парсит
`.proto`. Но для воспроизводимости стоит закрепить в CI конкретную **стабильную**
версию protoc и перегенерировать наш файл ею, чтобы шапка не прыгала от машины
к машине.

## 10. Отдельно: политика на бэкенде

Не входит в объём кика — политика живёт на бэкенде. Но объясняет, почему в
`SessionIP` два временных поля.

### 10.1 Модель сервиса

**Один uuid/email = одно устройство.** Каждый девайс получает свои креды, так
что две IP на одном uuid — уже неправильное использование. Базовая политика:
**кикнуть все IP кроме самого нового** (`since`).

### 10.2 Где эта модель даёт ложняк

Одно устройство может легально держать **два IP одновременно**:

| Случай | Почему две IP |
|---|---|
| Dual-stack IPv4/IPv6 | часть соединений по v4, часть по v6 — две разные строки `Source.Address.String()`. На мобильных операторах с IPv6 это норма |
| iOS Wi-Fi Assist / handoff | устройство реально открывает соединения через оба интерфейса сразу, а не последовательно |
| Ротация CGNAT | оператор сменил публичный IP посреди сессии, старые коннекты доживают на прежнем |

Во всех трёх «кикаем всё кроме нового» бьёт по честному одиночному устройству.
Хуже того, при handoff'е «самый новый» скачет туда-обратно — клиент кикает сам
себя в цикле, каждый раз с баном. Это ровно та проблема, от которой мы уходим,
в новой форме.

### 10.3 Что с этим делать

**Роль `lastSeen` — решать, кикать ли вообще** (а не кого):

- обе IP со свежим `lastSeen` → реальная одновременность, это шаринг;
- у старой `lastSeen` 30–40-секундной давности → это хвост, он сам умрёт по
  `connIdle`. Кик ничего не даёт, а шанс попасть в handoff — даёт.

**Гистерезис на бэке:** требовать, чтобы условие продержалось два опроса подряд
(~10 с) перед киком. Транзиентный dual-stack-флап отсеивается полностью, а
шарящий за 10 секунд никуда не денется. Стоит ноль, ядра не касается.

### 10.4 Известная дырка

Один длинный поток (видео, скачивание, ssh) даёт старый `lastSeen` при живом
трафике — такой IP будет выглядеть хвостом. Закрывает это только счётчик байт
на IP, а он требует обёртки ридеров/райтеров в реестре, то есть реальной новой
плумбинга. В v1 не тащим: сначала смотрим на проде, как часто ошибается.

## 11. Риски

| Риск | Митигация |
|------|-----------|
| `IsBanned` на горячем пути аутентификации | `atomic.Int64` счётчик активных банов, выход до взятия мьютекса, когда банов нет |
| Гонка «кикнули → мгновенный реконнект» | Бан ставится **до** закрытия коннектов |
| Hysteria2: кик рвёт стрим, а не сессию | Ожидаемо (§5.3); блокировка добирает остальное |
| Пустой email в hysteria до аутентификации | Явная проверка на непустой Email в §6.3 + тест |
| Mux/XHTTP: один conn = много потоков | Закроются все потоки этого коннекта. Тот же юзер и IP — приемлемо |
| Баны теряются при рестарте | Осознанно: для 5–10 с персистентность бессмысленна |
| Утечка handle при незакрытом ctx | Тот же `context.AfterFunc`, что у `OnlineMap`; периодический sweep как страховка |
| Расхождение с upstream | Диф ~12 строк в чужих файлах + CI из §13 |

## 13. CI: автосинхронизация с upstream

### 13.1 Модель веток

- `main` — наша ветка: upstream-тег `$BASE` плюс наши N коммитов.
- Файл `UPSTREAM_TAG` в корне хранит текущий `$BASE` (например `v25.8.3`).
- Ветки `sync/<tag>` создаёт CI, руками их не трогаем.

### 13.2 `.github/workflows/sync-upstream.yml`

Раз в сутки по cron + `workflow_dispatch`:

1. checkout с `fetch-depth: 0`;
2. добавить remote `upstream`, `git fetch upstream --tags`;
3. взять последний релизный тег: `git tag -l 'v*' --sort=-v:refname | head -1`;
4. если совпадает с `UPSTREAM_TAG` — выходим, делать нечего;
5. `git rebase --onto <new-tag> $BASE main` в ветке `sync/<new-tag>`;
6. обновить `UPSTREAM_TAG`, закоммитить;
7. **гейт** (см. 13.4 — «зелёный» ≠ весь репозиторий):
   - `go build ./...`
   - `go test ./app/fllcker/... ./app/dispatcher/...`
   - `go test ./infra/conf/ -run TestAPIConfig` — точечно, весь пакет красный
     из-за `TestGeodataConfig`
   - `go test -race ./app/fllcker/...` — реестр конкурентный, а локально на
     Windows race-детектор не собирается без gcc, так что CI — единственное
     место, где он вообще прогонится;
   - `go vet ./app/fllcker/... ./app/dispatcher/... ./proxy/hysteria/...`
   - `bash scripts/check-patches.sh` (см. [PATCHES.md](PATCHES.md));
8. пуш ветки и `gh pr create`;
9. при конфликте или красных тестах — `gh issue create` с логом и списком
   конфликтных файлов.

### 13.3 Почему PR, а не автомерж

Соблазн смержить автоматически при зелёном билде понятен, но:

**Чистый ребейз и зелёная сборка не ловят смысловой дрейф.** Upstream может
перестать заполнять `Inbound.Conn` для какого-то транспорта, поменять момент
вызова `WrapLink`, переписать hysteria-аутентификацию — всё это компилируется и
проходит юнит-тесты, а кик тихо перестаёт работать. Для прода VPN это худший
вид поломки: незаметный.

Ревью 12 строк раз в релиз — полминуты. Автомерж экономит эти полминуты и стоит
недели отладки в тот раз, когда не сработает.

Если всё же захочется автомержа — сначала завести e2e-смоук из §9 шага 8 как
обязательный job, и мержить только по нему, а не по `go build`.

### 13.4 Базовая линия: upstream сам по себе не зелёный

Проверено на чистом `7d214f8`, без наших правок:

| Команда | Состояние | Причина |
|---|---|---|
| `go build ./...` | ✅ зелёно | — |
| `go test ./...` | ❌ красно | `app/dns` требует сети; `app/router`, `common/geodata` и `infra/conf` (`TestGeodataConfig`) — файлов `geoip.dat`/`geosite.dat`, которых нет в репозитории |
| `go vet ./...` | ❌ красно | `possible misuse of unsafe.Pointer` в `proxy/vless/{inbound,outbound}` |

**Поэтому гейт нельзя вешать на весь репозиторий** — он будет красным всегда, и
очень быстро на него перестанут смотреть. Проверяем сборку целиком, а тесты и
`vet` — по нашим пакетам, перечисленным в 13.2.

Полный `go test ./...` имеет смысл держать отдельным **необязательным** job'ом:
он ловит настоящую регрессию, если upstream однажды сломает то, что раньше
работало. Но блокировать мерж он не должен.

### 13.5 `.github/workflows/release.yml`

На пуш тега `v*-fllcker`: сборка `linux/amd64` + `linux/arm64`, заливка
бинарников в GitHub Release. Иначе каждый апдейт форка — ручная сборка на
сервере.
